== Aufloesungsreihenfolge fuer Jenkinsfiles

Das Plugin loest die Pipeline-Datei in dieser Reihenfolge auf:

. `execution.jenkinsfile` aus `<organisation>/gretl-datenportal-job.yaml`
. `Jenkinsfile` im Organisationsordner
. `execution.jenkinsfile` aus `shared/gretl-datenportal-defaults.yaml`
. `shared/Jenkinsfile`

`shared/Jenkinsfile` ist damit der repo-weite Default-Fallback.

== Placeholder im impliziten Default

Nur das implizite repo-weite `shared/Jenkinsfile` wird als Template behandelt.
Dabei ersetzt das Plugin folgende Marker:

* `@@TIMEOUT_MINUTES@@`
* `@@GRADLE_TASK@@`
* `@@POST_BLOCK@@`

Die Werte stammen aus dem aufgeloesten `JobDefinition`- und
`NotificationConfiguration`-Modell.

== Wichtige Renderregeln

* Organisationsspezifische `Jenkinsfile`-Dateien werden unveraendert geladen.
* Explizite `execution.jenkinsfile`-Pfade werden unveraendert geladen.
* Unbekannte Marker bleiben unveraendert stehen.
* Wenn Notifications deaktiviert sind, setzt das Plugin einen einfachen
  Default-`post`-Block mit einer Abschlussmeldung ein.

== Warum diese Regel wichtig ist

Die Template-Behandlung bleibt absichtlich eng. Das Plugin rendert nur den
kanonischen repo-weiten Fallback, nicht beliebige Jenkinsfiles. Dadurch bleibt
die Default-Pipeline reproduzierbar, waehrend Organisationen bei Bedarf
weiterhin auf eine eigene Jenkinsfile ausweichen koennen.

Die Pipeline wird aus dem Jenkins-internen Repository-Snapshot gerendert. Im
`working-tree`-Modus ist das der Stand des letzten Seed-Laufs, nicht eine
Live-Sicht auf `THEMEN_REPO_PATH`. Deshalb müssen Änderungen am Arbeitsbaum
zuerst durch einen neuen Seed-Lauf materialisiert werden.
